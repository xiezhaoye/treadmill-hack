## 坑 1 ⭐⭐⭐：一次性订阅所有特征值 → 收不到任何数据

### 现象

连接成功、`CCCD status=0`、所有订阅都返回成功，但**一条通知数据都收不到**。

```
订阅 00002a05... setNotify=true   ← 都成功
订阅 00002ad3... setNotify=true
订阅 00002acd... setNotify=true
...
CCCD: status=0
→ 然后：什么都收不到
```

### 根因

**Android 的 GATT 队列一次只能处理一个 descriptor 写入。** 连续发 8 个 `writeDescriptor`，除了最后一个全部被丢弃。

### 解决

**逐个订阅，等每个 `onDescriptorWrite` 回调后再订阅下一个**：

```java
void subscribeNext(BluetoothGatt g) {
    if (subIdx >= subList.size()) { log("全部订阅完成"); return; }
    BluetoothGattCharacteristic ch = subList.get(subIdx);
    g.setCharacteristicNotification(ch, true);
    BluetoothGattDescriptor dd = ch.getDescriptor(CCCD);
    dd.setValue(BluetoothGattDescriptor.ENABLE_NOTIFICATION_VALUE);
    g.writeDescriptor(dd);
    // 等 onDescriptorWrite 回调 → subIdx++ → 再调 subscribeNext
}

@Override
public void onDescriptorWrite(BluetoothGatt g, BluetoothGattDescriptor d, int st) {
    subIdx++;
    ui.postDelayed(() -> subscribeNext(g), 150);   // 150ms 间隔
}
```

### 教训

**`setCharacteristicNotification()` 返回 true 和 `writeDescriptor()` 返回 true 都不代表成功。**
必须等 `onDescriptorWrite` 回调，检查 `status == 0`。

## 坑 2 ⭐⭐⭐：找错了解锁通道（UUID 字节序）

### 现象

抓包里明明看到 App 往 handle `0x03d` 写解锁码，但我连接后**找不到这个特征值**。

列出了全部 7 个服务、30 个特征值，没有 `5914fb69-...`。

### 根因

**128 位 UUID 的解析字节序错了。**

```python
原始字节: 5914fb69925255a3e8114cc4102c8dd1
❌ 错误（按小端）: 69fb1459-5292-a355-e811-4cc4102c8dd1
✅ 正确 UUID:     d18d2c10-c44c-11e8-a355-529269fb1459
```

**两个都不对**——因为 ATT 传输的是**大端**，但抓包工具给的原始 hex 需要仔细判断方向。

### 解决

**用 `props`（属性位）+ handle 位置交叉验证，不靠 UUID 字符串匹配**：

```
btsnoop 解析（小端）: value=0x03d  props=0x0c  uuid=69fb1459-5292-a355-e811-4cc4102c8dd1
Android API（实测）:                props=0x0c  uuid=d18d2c10-c44c-11e8-a355-529269fb1459
                    ↑ handle 0x03d 和 props 0x0c 完全一致
→ 同一个特征值，两个字符串都对，只是不同工具的展示差异
```

**实战做法**：不要只靠 UUID 字符串匹配。用 `props` 过滤：

```python
# 在 1826 服务里找 props == 0x0c（读+写）的那个
for ch in ftms_service.get_characteristics():
    if ch.getProperties() == 0x0c:
        unlock_channel = ch   # 找到了
```

### 教训

**当 UUID 对不上时，先看属性位和 handle 位置，别死磕字符串。**

## 坑 3 ⭐⭐⭐：MIUI 的 btsnoop 文件不在标准路径

### 现象

在小米手机上打开「蓝牙数据包日志」，用标准路径找不到文件：

```bash
$ adb shell "ls /sdcard/btsnoop_hci.log"
No such file or directory

$ adb shell "getprop persist.bluetooth.btsnoopenable"
（空）
```

**结论：以为 MIUI 的开关是假的**，我去折腾 root、找替代方案，浪费大量时间。

### 根因

**文件一直在生成**，只是在完全不同的路径：

```
/storage/emulated/0/MIUI/debug_log/common/btsnoop_hci.log
```

### 解决

```bash
# 全盘搜索
adb shell "find /sdcard /storage/emulated/0 -name '*btsnoop*' 2>/dev/null"
```

### 教训

**「标准位置没有」不等于「没有」。先全盘搜一遍。**

另外：`getprop persist.bluetooth.btsnoopenable` 为空**不代表功能没开**——MIUI 用别的机制控制。

## 坑 4 ⭐⭐：以为要写密码，实际不用

### 现象

一开始尝试用 `adb shell` 直接 `am startservice` 调用 Termux 的 RUN_COMMAND 服务执行命令：

```
Error: Requires permission com.termux.permission.RUN_COMMAND
```

### 根因

`RUN_COMMAND` 是**签名级权限**，需要 Termux 里手动开启 `allow-external-apps`，adb 无法授权。

### 解决

改用 Termux 的 `run-as`（因为 Termux 是 `debuggable`）：

```bash
adb shell "run-as com.termux files/usr/bin/bash -c 'your command'"
```

**注意**：只有 `debuggable` 的 App 能用 `run-as`。商用 App（如 YPOOFIT）不行。

## 坑 5 ⭐⭐：MIUI 重装 APK 后权限被悄悄撤销

### 现象

每次 `adb install -r` 重装 App 后，代码里 `checkSelfPermission` 返回 false：

```
权限检查 sdk=29 loc=false
!! 缺少蓝牙/定位权限
```

但 `adb shell pm grant` **报告成功**。

### 根因

**MIUI 的权限系统有两层**：
- `pm grant` 改的是 runtime permission（报告 granted=true）
- 但实际生效需要 **AppOps** 也为 allow

有时候 `dumpsys package` 显示 `granted=true`，实际 `granted=false`（缓存不一致）。

### 解决

**双管齐下**：

```bash
adb shell "pm grant com.example.app android.permission.ACCESS_FINE_LOCATION"
adb shell "cmd appops set com.example.app FINE_LOCATION allow"
adb shell "cmd appops set com.example.app COARSE_LOCATION allow"
```

### 教训

**MIUI 上装完 App 必须重新授权，而且必须用 `cmd appops`。**

## 坑 6 ⭐⭐：BLE 单连接限制——App 会抢连接

### 现象

跑步机连接着厂商 App 时，我的程序**扫描不到设备**（返回 0 个设备）。

### 根因

**BLE 外设通常只允许一个 central 连接**。被 App 连着时，它不再对外广播。

### 解决

测试前先 `am force-stop <厂商App>`，等 GATT 释放：

```bash
adb shell "am force-stop com.yp.yilian"
sleep 3
adb shell "dumpsys bluetooth_manager | grep -c '<跑步机MAC>'"   # 应该是 0
```

## 坑 7 ⭐⭐：macOS 上 adb 连不上局域网（本地网络隐私）

### 现象

在 macOS 上用 `adb connect 192.168.x.x:5555`：

```
failed to connect: No route to host
```

但同一个 IP，`curl` 和 `nc` 都能通。

### 根因

**macOS 的「本地网络」隐私权限按进程拦截。**

实测（同一台机、同一目标）：

| 工具 | 结果 |
|---|---|
| `/usr/bin/curl` | ✅ 通 |
| `/usr/bin/perl` | ✅ 通 |
| `/usr/bin/python3` | ❌ EHOSTUNREACH |
| `/usr/bin/ruby` | ❌ EHOSTUNREACH |
| `node` | ❌ EHOSTUNREACH |
| 自编译 C（`connect()`） | ❌ EHOSTUNREACH |

判据：`connect_ex()` **立即返回 65**（策略拒绝，不是超时）。

### 解决

三个选择：
1. 系统设置 → 隐私与安全性 → **本地网络** → 给终端打勾
2. 用**另一台机器**（Linux/Mac mini）跑 adb
3. 用 `adb_shell` 之类的 Python 库（不走 raw socket）

## 坑 8 ⭐：`settings put` 写不存在的组件不报错

### 现象

设置屏保组件名写错（`ClockScreensaver` vs `ClockDream`），`settings put` **返回成功**，但屏保没变。

### 教训

**Android 的 `settings put` 不会校验值是否存在。** 写完必须 `settings get` 读回验证。

## 坑 9 ⭐：`adb backup` 每次都要手机确认

### 现象

```bash
adb backup -f /tmp/app.ab -noapk com.yp.yilian
# → Now unlock your device and confirm the backup operation...
# → 文件 0 字节
```

### 原因

Android 会弹窗要求确认，**如果没点允许，备份会生成 0 字节文件**。

### 解决

脚本里要**检查文件大小**：

```python
import os
if os.path.getsize('/tmp/app.ab') < 1000:
    print("备份失败，请在手机上点「允许」")
```

## 坑 10 ⭐：`WRITE_TYPE_NO_RESPONSE` vs `WRITE_TYPE_DEFAULT`

### 现象

发 FTMS 指令用 `WRITE_TYPE_NO_RESPONSE`，写入返回 `ok=true`，但没响应。

### 根因

**FTMS 控制点 `2ad9` 是 Indicate 属性**，必须用 `WRITE_TYPE_DEFAULT`（带响应的写）。

### 对照

| 通道 | 正确写入方式 |
|---|---|
| `2ad9`（FTMS 控制点） | `WRITE_TYPE_DEFAULT` |
| `fff2`（私有通道） | `WRITE_TYPE_NO_RESPONSE` |
| 解锁通道 `d18d2c10` | `WRITE_TYPE_NO_RESPONSE` |

## 坑 11 ⭐：解锁后必须等 2 秒

### 现象

写完解锁码立即发 FTMS 指令，全部返回 `05`（拒绝）。

### 根因

**跑步机收到解锁码后会重置 GATT 会话**，之前的订阅全部失效。

### 解决

```
写解锁码 → 等 2 秒 → 重新订阅 8 个特征值 → 再发指令
```

### 教训

**时序很重要。** 抓包时按时间轴对齐看，能发现这类间隔。

## 坑 12 ⭐：误判"启动成功"

### 现象

第一次测试时，发了启动指令，看到 `写入完成 status=0`，跑步机在动，就以为成功了。

**实际跑步机本来就在以速度 1 转着**——是用户之前手动开的。

### 教训

**验证控制是否生效，不能只看「写入成功」，要看「状态变化」。**

正确做法：
1. 记录发送前的状态（数据帧里的速度字段）
2. 发送指令
3. 对比状态是否**变成了你发送的值**

我的验证方式：
```
发送 02f401 (5.0 km/h)
→ 数据帧从 0000 变成 f401
→ f401 = 500 = 5.00 km/h ✅ 确认生效
```

## 坑 13 ⭐：以为私有协议，实际是标准 FTMS

### 现象

一开始从 APK 里挖到私有服务 `fff0/fff1/fff2`，就照着私有协议逆向，挖出了 `a3`/`f5` 帧格式、CRC 校验……

**但发出去全部无效。**

### 根因

**App 实际用的是标准 FTMS（`0x1826`/`0x2ad9`）**，私有 `fff2` 是另一套（可能是给别的机型用的）。

### 教训

**先抓包看 App 实际发什么，再决定逆向什么。**

只看 APK 里的字符串，会被大量"看起来像协议"的常量误导。
