## 一、结论速览

| 项 | 结果 |
|---|---|
| 蓝牙类型 | **BLE（GATT）**，非经典蓝牙 |
| **协议（实测确认）** | ★ **标准 FTMS**（`0x1826`），控制点 `0x2ad9`。私有 `fff0/fff1/fff2` 是**另一套**，App 实际**不用** |

| 实测控制 | 🎉 **完全成功**：启动/调速/变坡/停止全部生效（2026-10-22 验证） |

## 六、★ CRC 校验算法（已破解并验证）

> 来源：`Lcom/yp/yilian/fly/utils/CRCUtils;` 的 `calcCRC` / `checkCRC`

### 6.1 算法（CRC16 变种，**厂商自定义多项式**）

```python
def calc_crc(hexstr: str) -> str:
    """输入十六进制字符串（含 f5 帧头），返回 4 位校验（高低字节已交换）"""
    data = bytes.fromhex(hexstr)
    crc = 0xFFFF                      # 初值
    for b in data:
        crc ^= b
        for _ in range(8):
            if crc & 1:
                crc = (crc >> 1) ^ 0xA327    # ★ 多项式：0xA327（41767）
            else:
                crc >>= 1
            crc &= 0xFFFF
    # ★ 最后高低字节交换
    return f"{((crc >> 8) & 0xFF) | ((crc << 8) & 0xFF00):04x}"
```

**与标准算法的对比**：

| 参数 | 本协议 | CRC16-MODBUS | CRC16-CCITT |
|---|---|---|---|
| 初值 | `0xFFFF` | `0xFFFF` | `0xFFFF` |
| **多项式** | **`0xA327`** ← 自定义 | `0xA001` | `0x1021` |
| 输入反转 | 否 | 否 | 否 |
| 输出反转 | 否 | 否 | 否 |
| 异或输出 | 无 | 无 | 无 |
| **字节序** | **交换** | 不交换 | 不交换 |

### 6.2 指令构造

```python
def build_cmd(payload: str) -> str:
    """payload 不含 f5 头、不含校验、不含 fa 尾"""
    body = "f5" + payload
    return f"f5{payload}{calc_crc(body)}fa"
```

**指令结构**：

```
f5  <payload>          <crc4>  fa
└─┘ └────────┘        └────┘  └┘
帧头   载荷(可变长)      校验   帧尾
      ↑
      CRC 计算范围 = "f5" + payload（含帧头！）
```

### 6.3 ✅ 用 App 内真实常量验证（4/4 全部通过）

| 指令 | 期望 | 算出 | 结果 |
|---|---|---|---|
| `08000504` | `f50800050499c2fa` | `f50800050499c2fa` | ✅ 启动 |
| `08000502` | `f508000502eee2fa` | `f508000502eee2fa` | ✅ 暂停 |
| `08000501` | `f508000501f251fa` | `f508000501f251fa` | ✅ 停止 |
| `08000904` | `f5080009041677fa` | `f5080009041677fa` | ✅ 解锁 |

### 6.4 `checkCRC` 的解析逻辑（逆向细节）

```java
if (data.length() <= 2) return false;
String body = data.substring(2, data.length() - 4);   // 去 "f5" 和末4位
String tail = data.substring(data.length() - 4);      // 末4位 = 校验
String calc = calcCRC("f5" + dataFormat(body, 2) + body);
return calc.equals(tail);
```

其中 `dataFormat(s, n)`（`PowerDataParseUtils.dataFormat`）只是**左侧补零补到 n 的倍数**，对已对齐的数据无影响。

## 八、⚠️ 为什么不能让 Mac 直接连（两个硬限制）

### 8.1 物理限制：蓝牙够不着

```
M1 / 5095   → 书房
跑步机       → 阳台
```

BLE 有效距离 10 米级，隔墙更短。**Mac 从书房连不到阳台的跑步机。**

### 8.2 协议限制：Mac 扫不到它

实测（§2.1）：macOS BLE 扫描 15 秒，17 个设备里**没有** `YPOO-M5-008264`。
即使搬到跑步机旁边，它可能也只对已配对的特定主机响应。

└─────────────┘   199.196    └──────────────┘            └──────────┘

**手机就是伸到阳台的"蓝牙天线"**，已具备全部前提：

| 前提 | 状态 |
|---|---|
| 手机与 Mac 同网段 | ✅ `192.168.199.196`（WiFi `xiaoyuan_5G`） |
| 无线 ADB | ✅ `192.168.199.196:5555`，已在 5095 上验证 `device` 状态 |

### 9.2 在手机上跑 BLE 客户端的三种方案

| 方案 | 做法 | 优缺点 |
|---|---|---|
| **A. Termux + Python + bleak**（推荐） | 手机装 Termux，`pkg install python`，`pip install bleak`，跑自定义脚本 | 灵活、可迭代；Termux 需从 F-Droid 装 |

## 十、登录与验证码问题（已排查，非 App bug）

### 10.1 现象

- ❌ iPhone「未知发件人」分类 —— 查了，没有

## 十三、踩过的坑（教训）

| 坑 | 教训 |
|---|---|
| **MIUI 的「蓝牙数据包日志」是假开关** | 打开后 `persist.bluetooth.btsnoopenable` / `btsnooplogmode` **始终为空**，`/sdcard/btsnoop_hci.log` 不存在。`setprop` 被拒（shell 无 root）。**MIUI 上别指望 HCI 日志。** |
| **HTTPS 中间人抓包走不通** | App `targetSdk=35` → 不信任用户证书；手机无 root → 装不进系统证书区。`network_security_config` 只对 `192.168.103.203` 允许明文。 |

| **Android 10 不能 `adb backup`** | 需要 App 显式开启 `allowBackup`（虽然有 `allowBackup=true`，但 Android 10 已限制） |
| **m1 连不了局域网** | macOS 本地网络隐私按进程拦截（见 `安卓盒子-192.168.199.170.md` §8.1）→ **所有 adb 操作走 5095** |
| **`adb shell input keyevent` 不走无障碍** | `injectKeyEvent` 直接注入，绕过无障碍服务 → 模拟按键测不出真实遥控器行为 |

### 15.2 解析方法

btsnoop 格式：16 字节头 + N 条记录，每条 24 字节头 + 数据。

```python
import struct
d = open('btsnoop_hci.log','rb').read()
pos = 16
recs = []
while pos + 24 <= len(d):
    orig_len, incl_len, flags, drops, ts_sec, ts_usec = struct.unpack('>IIIIII', d[pos:pos+24])
    pos += 24
    pkt = d[pos:pos+incl_len]; pos += incl_len
    recs.append((ts_sec + ts_usec/1e6, pkt[0], pkt[1:]))   # pkt[0] = HCI 类型
```

**HCI 类型（`pkt[0]`）**：
| 值 | 含义 |
|---|---|
| `0x01` | HCI Command |
| `0x02` | **ACL 数据**（GATT 走这个） |
| `0x04` | HCI Event |

**ACL → L2CAP → ATT**：
```python
# pkt[1:] 是 ACL 数据
handle = struct.unpack('<H', pkt[0:2])[0] & 0x0FFF
dlen   = struct.unpack('<H', pkt[2:4])[0]
body   = pkt[4:4+dlen]
l2len  = struct.unpack('<H', body[0:2])[0]
cid    = struct.unpack('<H', body[2:4])[0]
if cid == 4:                      # ATT
    att = body[4:4+l2len]
    opcode = att[0]
```

**ATT opcode**：`0x52`=WriteCmd，`0x12`=WriteReq，`0x1b`=Notify，`0x1d`=Indicate，`0x13`=WriteResp

**⚠️ 128 位 UUID 是小端存储**：
```python
import uuid
uuid.UUID(bytes_le=bytes.fromhex("5914fb69925255a3e8114cc4102c8dd1"))
# → 69fb1459-5292-a355-e811-4cc4102c8dd1
```

### 15.5 ★ FTMS 控制指令全集（实测验证）

| 指令 | 含义 | 备注 |
|---|---|---|
| `00` | **Request Control** | 必须先发，跑步机回 `800001` 表示成功 |
| `07` | Start / Resume | 启动或继续 |
| `0801` | Stop / Pause | 暂停 |
| `02<xx><xx>` | Set Target Speed | 速度 × 100，小端 2 字节。例：`02c800` = 200 = **2.0 km/h** |
| `03<xx><xx>` | Set Target Inclination | 坡度 × 10，小端 2 字节。例：`030a00` = 10 = **1.0%** |
| `01` | Reset | — |

**响应格式**：`80` + `<opcode>` + `<result>`
```
800001 → 00 成功
800201 → 02 成功
800801 → 08 成功
```

## 十五、★★★ 完整控制成功（2026-10-22 实测验证）

### 16.1 决定性突破：找到解锁通道

**关键洞察：抓包解析出的 `5914fb69-...` 是解析错误，实际 UUID 是 `d18d2c10-c44c-11e8-a355-529269fb1459`。**

识别方法：**对比 `props` 属性**。

```
抓包：  decl=0x03c  props=0x0c  uuid=5914fb69-...(解析错误)
实测：             props=0x0c  uuid=d18d2c10-c44c-11e8-a355-529269fb1459
                    ↑ 0x0c = 读+写，在 1826 服务里唯一
```

> **教训**：btsnoop 里 128 位 UUID 的字节序解析极易出错。**用 `props`（属性位）交叉验证**是可靠方法。

### 16.2 ★ 完整控制流程（4 步，缺一不可）

```python
# ① 写解锁码（不可跳过！）
#    目标：d18d2c10-c44c-11e8-a355-529269fb1459  (props=0x0c)
#    数据：0123456789ABCDEF  (从 App MMKV 的 unlock_code 取)
#    写入方式：WRITE_TYPE_NO_RESPONSE

# ② 等 2 秒 —— 跑步机会重置 GATT 会话

# ③ 顺序订阅 8 个特征值（⚠️ 必须逐个，等每个 CCCD 完成再下一个）
#    2a05(INDICATE), 2ad3, 2acd, 2ad9(INDICATE), 2ada, fff1, ffc1, 02f0...ff02
#    ↓ 一次性订阅 8 个会失败（Android GATT 队列限制）→ 之前一直收不到数据就是这个原因

# ④ 向 2ad9 发 FTMS 指令（WRITE_TYPE_DEFAULT）
```
