# 抓包教程

> 目标：拿到跑步机与 App 之间的**完整蓝牙通信字节流**。
> 本文以 Android 手机为例（不需要 root）。

---

## 一、原理

Android 的蓝牙协议栈可以把所有 HCI（Host Controller Interface）数据包记录成 **btsnoop** 文件，
格式与 Wireshark 兼容。里面包含：

- 扫描过程（发现设备）
- 连接建立
- **所有 GATT 读写**（你需要的东西）
- 通知数据

---

## 二、开启日志（分品牌）

### 2.1 通用路径

```
设置 → 关于手机 → 连按「版本号」7 次 → 开启开发者选项
→ 返回设置 → 系统 → 开发者选项
→ 找到「启用蓝牙 HCI 信息收集日志」/「蓝牙数据包日志」
→ 打开
```

**打开后必须重启一次蓝牙**（下拉通知栏关掉再打开）。

### 2.2 各品牌位置

| 品牌 | 路径 |
|---|---|
| **小米 / Redmi / MIUI / HyperOS** | 设置 → 更多设置 → 开发者选项 → 启用蓝牙 HCI 信息收集日志 |
| 华为 / 荣耀 | 设置 → 系统和更新 → 开发人员选项 |
| OPPO / 一加 / realme | 设置 → 其他设置 → 开发者选项 |
| vivo / iQOO | 设置 → 系统管理 → 开发者选项 |
| 原生 Android / Pixel | 设置 → 系统 → 开发者选项 → 启用蓝牙 HCI 信息收集日志 |
| 三星 | 设置 → 开发者选项 → 蓝牙 HCI 信息收集日志 |

## 三、日志文件在哪

### 3.1 标准路径

```
/sdcard/btsnoop_hci.log
或
/data/misc/bluetooth/logs/btsnoop_hci.log    （需要 root）
```

### 3.2 ⚠️ MIUI / HyperOS 的坑

**小米把文件放在完全不同的位置**：

```
/storage/emulated/0/MIUI/debug_log/common/btsnoop_hci.log
```

**我花了很久才找到**——标准路径下没有，一度以为 MIUI 的开关是假的。

**一键查找**：
```bash
adb shell "find /sdcard /storage/emulated/0 -name '*btsnoop*' 2>/dev/null"
```

## 四、抓包流程

### 4.1 准备

```bash
# 1. 记录当前文件大小（方便对比）
adb shell "ls -la /storage/emulated/0/MIUI/debug_log/common/btsnoop_hci.log"

# 2. 清空旧日志（可选，但如果文件很大建议清）
#    方法：关掉日志开关 → 再打开（会重新生成）
```

### 4.2 操作 App

**关键：慢一点，每步之间留几秒**，方便后面按时间轴对齐。

```
1. 打开厂商 App
2. 搜索设备          ← 停留 3-5 秒
3. 点击绑定          ← 停留 3-5 秒
4. 扫码（如果需要）   ← 停留 5 秒
5. 进入操控界面       ← 停留 10 秒
6. 点启动            ← 停留 10 秒
7. 调速到 2          ← 停留 5 秒
8. 调速到 3          ← 停留 5 秒
9. 调坡度            ← 停留 5 秒
10. 暂停             ← 停留 5 秒
11. 停止             ← 停留 10 秒
```

### 4.3 拉取文件

```bash
# 一键拉取（自动查找路径）
./tools/pull-btsnoop.sh

# 或手动
adb pull /storage/emulated/0/MIUI/debug_log/common/btsnoop_hci.log ./btsnoop.log
```

## 五、验证文件有效

```bash
xxd btsnoop.log | head -3
```

**正确输出**：
```
00000000: 6274 736e 6f6f 7000 0000 0001 0000 03ea  btsnoop.........
00000010: 0000 0004 0000 0004 0000 0002 0000 0000  ................
```

| 偏移 | 含义 | 期望值 |
|---|---|---|
| 0x00 | magic | `btsnoop\0` |
| 0x08 | version | `1` |
| 0x0C | **datalink** | `1002`（HCI USB）或 `1001`（HCI UART） |

**如果 datalink 不是 1001/1002，说明抓的不是蓝牙流量。**

## 六、解析

```bash
./tools/parse-btsnoop.py btsnoop.log
```

会输出：

- 服务表（`Read By Group Response`）
- 特征值表（`Read By Type Response`）
- **所有写入指令**（按时间排序，含 handle 和十六进制数据）
- 所有通知数据

### 6.1 关键 ATT Opcode

| Opcode | 名称 | 含义 |
|---|---|---|
| `0x52` | Write Command | **写（无响应）** ← 指令 |
| `0x12` | Write Request | **写（带响应）** ← 指令 |
| `0x1B` | Handle Value Notification | **通知** ← 数据 |
| `0x1D` | Handle Value Indication | **指示** ← 响应 |
| `0x13` | Write Response | 写确认 |
| `0x09` | Read By Type Response | 特征值列表 |
| `0x11` | Read By Group Response | 服务列表 |

### 6.2 ⚠️ 128 位 UUID 的字节序陷阱

BLE 的 128 位 UUID 是**小端**存储，但 ATT 协议传输时是**大端**。解析错了会得到完全错误的 UUID。

**我的真实教训**：

```
抓包原始字节: 5914fb69925255a3e8114cc4102c8dd1
错误解析（小端）: 69fb1459-5292-a355-e811-4cc4102c8dd1  ← 找不到这个特征值
正确 UUID（实测）: d18d2c10-c44c-11e8-a355-529269fb1459  ← 这才是真的
```

**如何避免**：用**属性位（props）交叉验证**。

```python
# 从抓包看：decl=0x03c, props=0x0c (读+写)
# 从实际连接看：只有 d18d2c10-... 的 props 是 0x0c
# → 它们必然是同一个特征值
```

## 七、如果抓不到

| 现象 | 原因 | 解决 |
|---|---|---|
| 找不到 btsnoop 文件 | 路径不同 | `find / -name '*btsnoop*'` |
| 文件不增长 | 开关没生效 | 关掉蓝牙 → 再打开 → 再操作 |
| datalink 不是 1002 | 抓的是别的东西 | 确认是蓝牙日志文件 |
| **有 ATT 包但没有数据内容** | 正常 | **用 `parse-btsnoop.py` 解析，原始 hex 里没有明文** |
| 开了日志但还是没有 | 部分 ROM 屏蔽 | 换一台手机 / 或考虑 root 后开系统级日志 |

## 八、其他平台的抓包方式

| 平台 | 方式 | 难度 |
|---|---|---|
| **Android** | HCI btsnoop（本文） | ⭐ 最简单 |
| iOS | 需越狱 + tweak | ⭐⭐⭐⭐ 很难 |
| macOS | 系统不提供 HCI 日志 | ⭐⭐⭐⭐⭐ 基本不可行 |
| **专用硬件** | nRF Sniffer（~¥100）/ Ubertooth（~¥1000） | ⭐⭐ 花钱但彻底 |

**结论：找一台 Android 手机是最经济的方案。**
