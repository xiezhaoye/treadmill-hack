# ESP32 与跑步机连接机制详解

> 本文解释 ESP32-S3（ESPHome）如何发现、连接、控制跑步机，以及数据是如何流动的。
> 对照实际配置：`treadmill.yaml`、`components/treadmill/sensor/tm_data_handler.h`

---

## 零、一句话总览

```
跑步机广播 BLE ──► ESP32 扫描到 ──► 自动连接 ──► 服务发现
                                                    │
                     ┌──────────────────────────────┘
                     ▼
              自动解锁 + 请求控制权（只做一次握手）
                     │
        ┌────────────┴────────────┐
        ▼                         ▼
  订阅 0x2ACD               写入 0x2AD9
  （被动收数据）             （主动发指令）
        │                         │
        ▼                         ▼
  ESP32 每 0.4~0.5 秒        启动/调速/变坡/停止
  收到一帧速度+坡度
```

---

## 一、连接是怎么建立的

### 1.1 ESP32 是主动方，跑步机是被动方

**BLE 的角色划分是固定的**：

| 角色 | 是谁 | 职责 |
|---|---|---|
| **GATT Client（客户端）** | ESP32 | 主动扫描、发起连接、发读写请求 |
| **GATT Server（服务端）** | 跑步机 | 被动广播、接受连接、提供数据与接受指令 |

跑步机自己**不会**去连 ESP32。它只是不停地向外发广播包（advertising），说"我在这儿，我叫 `AA:BB:CC:DD:EE:FF`"。ESP32 听到后主动发起连接。

### 1.2 完整连接时序

```
① 跑步机通电 → 蓝牙模块启动 → 开始周期性广播
                （广播包约每 100ms 一次，含 MAC + 设备名 + 服务 UUID）

② ESP32 常驻扫描
   配置：interval=320ms, window=160ms, active=true
   ——每 320ms 里开 160ms 的接收窗口，占空比 50%

③ ESP32 在广播里看到目标 MAC（AA:BB:CC:DD:EE:FF）
   └─ 这就是"绑定"——绑定只是一个 MAC 地址，写在配置里
      配置项：ble_client → mac_address: "AA:BB:CC:DD:EE:FF"

④ ESP32 主动发起 BLE 连接（GATTC Open）
   └─ 日志：ESP_GATTC_CONNECT_EVT → ESP_GATTC_OPEN_EVT → "Connection open"

⑤ 连接建立后，ESP32 请求服务发现（Service Discovery）
   └─ 跑步机把自己的"能力清单"发过来：有哪些服务、哪些特征值
   └─ 日志：ESP_GATTC_SEARCH_CMPL_EVT → "Service discovery complete"

⑥ ESP32 在清单里找到需要的两个特征值：
   - 00002AD9-...  FTMS 控制点（写入指令）
   - D18D2C10-...  厂商解锁通道（写解锁码）
   - 00002ACD-...  FTMS 跑步机数据（订阅通知）

⑦ ESP32 订阅 0x2ACD（register_for_notify）
   └─ 之后跑步机会每 0.4~0.5 秒主动推送一帧数据
   └─ 日志："已订阅 0x2ACD (handle=0x0025)" → "notify 注册成功"

⑧ 自动握手（连接成功后 ESP32 自动执行）
   a. 等 2 秒（等服务发现彻底完成）
   b. 写解锁码到 D18D2C10（8 字节：01 00 00 00 08 0B 08 07）
   c. 等 2 秒（跑步机会重置 GATT 会话，必须等）
   d. 写 0x00 到 00002AD9（Request Control，请求控制权）
   e. 完成后 ESP32 就"有资格"控制跑步机了
```

### 1.3 绑定只做一次，但"配对"其实没做

**关键区别：**

| 概念 | 有没有 | 说明 |
|---|---|---|
| **绑定（配置 MAC）** | 有，只做一次 | MAC 写死在 `treadmill.yaml`，改了要重新烧录 |
| **BLE 配对/绑定（pairing）** | **没有** | 跑步机不要求配对，ESP32 直接连就行 |
| **会话** | 每次连接重建 | 每次连上都要重新解锁 |

所以：

- **MAC 地址** → 一次性配置，永久生效
- **解锁码** → 每次连接后都要重写（跑步机重启/断连后失效）
- **控制权** → 每次连接后都要重新请求

> 这就是为什么配置里把「解锁 + 请求控制」放在 `on_connect` 里自动执行——每次连接都得重做一遍。

## 二、什么时候连、什么时候断

### 2.1 触发连接的条件：跑步机的广播

ESP32 **一直在扫描**（`auto_connect: true`），不看时间、不看别的，只看一件事：

> **能不能在广播里听到 `AA:BB:CC:DD:EE:FF`。**

所以真实情况是：

| 跑步机状态 | 有没有广播 | ESP32 能否连上 |
|---|---|---|
| **通电但屏幕不亮**（深度待机） | ❌ 大多数情况不广播 | ❌ 连不上 |
| **屏幕亮起**（唤醒） | ✅ 广播 | ✅ 连上 |
| **跑带运转中** | ✅ 广播 | ✅ 连上 |
| **断电** | ❌ 无广播 | ❌ 连不上 |

**实测证据**（2026-10-23）：跑步机刚通电时 ESP32 扫不到；按下中间面板按钮、屏幕亮起后立刻扫到并连上。

### 2.2 为什么"通电但不亮屏"连不上

两个原因叠加：

1. **蓝牙模块可能没供电**。很多跑步机的蓝牙模块由主控板控制，深度待机时会切断蓝牙供电。
2. **即使供电也不广播**。有些跑步机待机时停止广播以省电，必须被物理按键唤醒。

**这是硬件限制，软件无法绕过。** 所以每次使用跑步机的第一步必然是你手动按一下面板按钮。

### 2.3 断开的情况

ESP32 会在以下情况断开（`on_disconnect` 触发）：

| 原因 | 代码 | 说明 |
|---|---|---|
| 跑步机断电/休眠 | `reason 0x08`（连接超时） | 最常见的 |
| 距离过远 | `reason 0x08` | RSSI 低于 -90 dBm 时容易掉 |
| 手机 App 抢占连接 | `reason 0x13` 等 | BLE 单连接限制，见下 |
| ESP32 重启 | — | 重启后会自动重连 |

### 2.4 ⚠️ BLE 单连接限制

**跑步机的 BLE 同一时刻只能被一个中心设备连接。**

```
跑步机 ──连接──► ESP32        （手机 App 就连不上）
跑步机 ──连接──► 手机 App      （ESP32 就连不上）
```

如果你用手机厂商 App 连了跑步机，ESP32 会掉线；反过来也一样。

**这也是之前排查时"断电重插"有效的原因**——强制清掉旧的 BLE 会话。

### 2.5 重连是自动的

断开后 ESP32 **不需要任何操作**会自动重连：

```yaml
ble_client:
  - mac_address: ${treadmill_mac}
    auto_connect: true        # ← 默认就是 true
```

只要跑步机重新开始广播，ESP32 在下一次扫描窗口就能扫到并连上。通常延迟在 **1 秒内**。

## 三、数据是怎么抓的

### 3.1 推送模型：跑步机主动推，ESP32 被动收

**不是 ESP32 去"问"，而是跑步机主动"报"。**

```
跑步机 ──每 0.4~0.5 秒推一帧──► ESP32
             （NOTIFY，无需请求）
```

订阅一次之后，数据就源源不断推过来，**即使跑步机静止不动也照推**（速度报 0）。

实测：静止状态下也是 0.418~0.482 秒一帧，约 **2.2 帧/秒**。

### 3.2 你按"开始"时发生了什么

**场景**：跑步机屏幕亮着 → 你按面板上的"开始" → 速度变 1 km/h

```
t=0.0s   你按"开始"（跑步机本地操作，不经过 ESP32）
t=0.1s   跑带开始转
t≈0.3s   跑步机推送下一帧数据
          9c 25 64 00 00 00 ...
                ↑     ↑
                速度   坡度
                0x0064 = 100 → 100/100 = 1.00 km/h
t≈0.3s   ESP32 收到 → 解析 → 发布 treadmill_current_speed = 1.0
t≈0.3s   页面上立刻显示 1.00 km/h
```

**结论：ESP32 能自动抓到，延迟约 0.5 秒以内。**

### 3.3 帧格式（298 帧逐帧实测确认 2026-10-24）

```
字节偏移   内容                说明
──────────────────────────────────────────────────────────────
0-1        9c 25              帧头（固定）
2-3        速度 × 100  小端    0x01c2 = 450 → 4.50 km/h
4-5        累计距离 × 10 小端  2 km/h 跑 18 秒 +10 → 单位为米
6-7        坡度 × 10   大端    0x0028=40→4.0%, 0x003c=60→6.0%, 0x0050=80→8.0%
8-10       00 ff 7f           固定值
11+        递增计数            跑动时递增
总长度     26 字节
```

**⚠️ 关键陷阱：`[6:8]` 是【大端】，而 `[2:4]`、`[4:6]` 是【小端】。混用！**

验证过程（用户设 4% → 6% → 8%）：

```
11:39:37   [6:8]=0x0028=40  → 4.0%   ← 设 4%
11:40:08   [6:8]=0x003c=60  → 6.0%   ← 设 6%
11:40:33   [6:8]=0x0050=80  → 8.0%   ← 设 8%
11:40:59   [6:8]=0x0000=0   → 0%     ← 停机归零
```

### 3.3.1 走过的一个大弯路

最初把 `[4:6]`（累计距离）当成坡度，导致：

```
02:20   3.0%
02:24  33.0%
02:28  63.0%
02:36 123.0%     ← 每 2 分钟匀速涨 15%，明显不是坡度
```

**教训**：坡度这类"应该稳定"的量如果出现匀速增长，一定是读错了字段——
匀速增长的量是累计值（时间/距离/计数）。

**实际抓到的帧**（静止状态）：

```
data=[9c 25 00 00 00 00 00 00 00 ff 7f 00 00 00 00 00 00 00 00 00 00 00 00 00]
      帧头 速度=0 坡度=0
```

**跑步中的帧**（速度 1 km/h）：

```
data=[9c 25 64 00 00 00 ...]
      帧头 速度=100 → 1.00 km/h
```

**立起来时的帧**（坡度约 30 度）：

```
treadmill_current_incline = 57.0 %    ← 约 29.7 度的物理倾角
```

> 注：坡度字段的物理含义是"跑台相对水平面的倾角"，立起来收纳时自然是一个大值。

### 3.4 抓取的是实时值，不是历史

每一帧都是**当前瞬间**的速度和坡度，没有历史、没有累计。

ESP32 收到后做两件事：

```cpp
// 1. 首帧必发（否则 0→0 的差值判断会跳过）
if (!got_first_frame_) { 发布; return; }

// 2. 之后只在变化时才发布（省带宽）
if (fabsf(新速度 - 旧速度) > 0.01) 发布;
if (fabsf(新坡度 - 旧坡度) > 0.05) 发布;
```

所以 Home Assistant 里看到的是**变化时更新**（不是每次推送都刷新），但数值永远是跑步机的最新状态。

## 四、控制是怎么发的

### 4.1 写入模型：ESP32 主动写，跑步机执行

与数据方向相反——控制指令是 **ESP32 主动写** 到 `00002AD9`（FTMS 控制点）：

| 动作 | 写入字节 | 含义 |
|---|---|---|
| 请求控制权 | `00` | Request Control |
| 启动 | `07` | Start |
| 停止 | `08 01` | Stop |
| 暂停 | `08 02` | Pause |
| 设速度 | `02 <lo> <hi>` | 速度×100 小端（`02 f4 01` = 5.0 km/h）|
| 设坡度 | `03 <lo> <hi>` | 坡度×10 小端（`03 28 00` = 4.0%）|

### 4.2 为什么必须先"请求控制权"

FTMS 协议规定：**客户端必须先获得控制权，才能发启动/调速指令。** 否则跑步机会拒绝执行。

这也是自动握手流程的最后一步，不可省略。

### 4.3 解锁码的作用

`D18D2C10-C44C-11E8-A355-529269FB1459` 是**厂商自定义特征值**，不是 FTMS 标准。

跑步机要求客户端先写一个 8 字节解锁码（`01 00 00 00 08 0B 08 07`），才允许后续对控制点的写入生效。

**这个解锁码是绑定到会话的**：跑步机断开重连后失效，必须重写。

## 五、完整流程总结

### 5.1 首次配置（只做一次）

```
① 从 App 抓包拿到 MAC 和 解锁码
② 写进 treadmill.yaml
③ 烧录固件
④ 之后 MAC 就固定了，不用再管
```

### 5.2 每次使用的完整流程

```
【你】跑步机通电
   ↓
【你】按面板中间按钮 → 屏幕亮 → 跑步机开始广播
   ↓  （约 1 秒内）
【ESP32】扫描到 MAC → 主动连接 → 服务发现
   ↓  （约 1 秒）
【ESP32】订阅 0x2ACD  →  开始收到数据帧（2.2 帧/秒）
   ↓  （自动，等 2 秒）
【ESP32】写解锁码 → 等 2 秒 → 请求控制权
   ↓
【状态】✅ 完全可控，数据实时上报
   ↓
【你】在页面点「启动」/ 调速 / 变坡
   ↓
【ESP32】写指令到 0x2AD9
   ↓
【跑步机】执行
   ↓
【跑步机】推新数据帧
   ↓
【ESP32】更新 sensor → 页面显示
```

### 5.3 你能做什么、不能做什么

| 操作 | 能否通过 ESP32 | 说明 |
|---|---|---|
| 连接跑步机 | ✅ 自动 | 只要你按了面板按钮 |
| 读速度/坡度 | ✅ 实时 | 2.2 帧/秒 |
| 启动跑带 | ✅ | 写 `07` |
| 调速 | ✅ | 写 `02 ...` |
| 变坡 | ✅ | 写 `03 ...` |
| 停止 | ✅ | 写 `08 01` |
| **唤醒屏幕** | ❌ | 物理按键，BLE 做不到 |
| **给跑步机通电** | ❌ | 硬件开关 |
| **断电** | ❌ | 硬件开关 |

## 六、常见问题

### Q1：为什么跑步机通电后 ESP32 连不上？

因为跑步机深度待机时**不广播 BLE**。必须按面板按钮唤醒。

### Q2：需要每次重新配对吗？

不需要配对（跑步机不要求 pairing）。MAC 地址配一次就行。

但**每次连接后都要重新解锁**，这个已经自动化了。

### Q3：手机 App 和 ESP32 能同时连吗？

不能。BLE 单连接限制，二者互斥。用 App 时 ESP32 会掉线，关掉 App 后 ESP32 会自动重连。

### Q4：数据延迟多大？

约 0.4~0.5 秒（一帧的时间）。跑步机一变速，页面最多半秒后就能看到。

### Q5：跑步机静止时会断连吗？

不会。跑步机静止时仍在推数据（速度 0），连接保持。

但如果屏幕熄灭（进入深度待机），BLE 断开，数据停止。

### Q6：ESP32 断电重启后会怎样？

自动重新扫描 → 扫到跑步机就重连 → 自动解锁 → 恢复可控。全程无需干预。

前提是跑步机当时处于广播状态（屏幕亮着）。

**特殊场景：跑步机正在运转时，ESP32 才上电** —— 见下一节详述。

## 6.1 特殊场景：跑带运转中 ESP32 才上电

### 时序

```
t = 0s      前提：跑步机已在运行（比如 5 km/h），屏幕亮着，持续广播
            此时没有 ESP32 连接，跑步机处于「本地手动控制」状态

t = 0s      你给 ESP32 通电
t ≈ 2s      ESP32 启动，WiFi 开始连接
t ≈ 8s      WiFi 连上，获取 IP
t ≈ 10s     on_boot 里配置的 delay 10s 结束（等 BLE 栈就绪）
t ≈ 11s     开始 BLE 扫描
t ≈ 11~12s  扫到跑步机 MAC → 主动发起连接
t ≈ 12s     Connection open → 服务发现
t ≈ 12.5s   订阅 0x2ACD 成功 → 立即收到第一帧
            帧内容：9c 25 f4 01 ...
                          速度 0x01f4 = 500 → 5.00 km/h
t ≈ 12.5s   ✅ 页面显示 5.00 km/h（真实值，非 0）

t ≈ 14.5s   on_connect 的 delay 2s 结束
t ≈ 14.5s   自动写解锁码到 D18D2C10
t ≈ 16.5s   自动写 0x00 到 0x2AD9（请求控制权）
t ≈ 17s     握手完成，ESP32 获得控制权
```

**跑带全程一直在转，ESP32 不会打断它。**

### 关键行为

| 项目 | 表现 |
|---|---|
| 跑步机会不会停？ | **不会。** ESP32 上电不发送任何停止指令 |
| 数据能否立刻读到？ | **能。** 订阅成功后第一帧就是真实速度 |
| 会不会自动接管控制权？ | **会。** 握手流程无条件执行 |
| 页面显示什么？ | 真实速度（如 5.0 km/h），状态标「运行中」 |

### ⚠️ 潜在风险

ESP32 自动握手后**获得了控制权**，这意味着：

```
任何时候误触页面按钮 → 跑步机立即响应
```

具体风险场景：

| 误操作 | 后果 |
|---|---|
| 碰到速度滑块 | 跑带**立刻变速**（比如从 5.0 突降到 0.5） |
| 点到「停止」 | 跑带**立刻停**（运动中急停有摔倒风险） |
| 点到「暂停」 | 同上 |
| 拖动坡度滑块 | 跑带**运动中变坡** |

**特别注意**：页面上的 `treadmill_speed` 控件显示的是"设定值"，默认 0.5，**不代表跑步机当前速度**。如果误触这个滑块，会真的把跑步机设成 0.5 km/h。

### 当前采用的策略

**保持现状**（不做额外保护），理由是：

- 日常使用中，跑步机静止 → ESP32 上电 → 自动就绪，体验流畅
- 运动中才上电属于少见场景
- 一旦发生，只要不碰页面就不会影响跑步机

### 如果需要更安全的方案

有三种可选改法（**当前未启用**）：

**方案 A：运动中不自动接管**

```yaml
on_connect:
  then:
    - delay: 2s
    - lambda: |-
        if (id(tm_speed_kmh) > 0.1f) {
          ESP_LOGW("treadmill", "跑步机运行中 %.1f km/h，跳过自动握手", id(tm_speed_kmh));
          return;
        }
    # ... 正常握手
```

效果：跑带转着时 ESP32 只读不控，页面按钮无效。等跑带停了、重连一次才自动接管。

**方案 B：加显式「接管控制」开关**

默认不请求控制权，需要控制时手动点一下。最安全，但每次都要多一步。

**方案 C：速度/坡度控件在运行中锁定**

检测到 `current_speed > 0` 时禁用滑块，避免误触。

> 推荐组合：**方案 A + 方案 C**。静止时无感，运动中防误操作。

## 八、踩过的坑（重要经验）

### 8.1 ESPHome 2026.10 的 API 变更

| 变更 | 影响 | 解决 |
|---|---|---|
| `ble_client::hex_to_bytes` 被移除 | 解锁码无法转换 | 自写 `hex_helper.h` |
| `custom` 组件被移除 | 无法用 lambda 解析原始字节 | 改用外部组件 `components/treadmill/` |
| `ble_client` 的 characteristic 传感器只给 `float` | 拿不到原始字节 | 继承 `BLEClientNode` 直接挂 GATTC 回调 |
| 中文实体名 ASCII ID 冲突 | 配置校验失败 | 实体名改英文 |
| `logger` 组件级别不能高于全局 | 配置校验失败 | 全局设 DEBUG |

### 8.2 日志 tag 必须显式声明

自定义组件的日志如果用 `ESP_LOGI("treadmill", ...)`，必须在 logger 配置里显式声明：

```yaml
logger:
  logs:
    treadmill: DEBUG     # ← 不写这行，日志会被 component:WARN 兜底压制
```

**否则日志完全不输出，会误判成"组件没运行"。** 这个坑排查了很久。

### 8.3 首帧必须强制发布

```cpp
// ❌ 错误：初始值 0，数据也是 0，差值判断永远跳过
if (fabsf(spd - speed_kmh_) > 0.01f) { 发布(); }

// ✅ 正确：首帧无条件发布
if (!got_first_frame_) { got_first_frame_ = true; 发布(); return; }
```

### 8.4 GATTC 事件编号易混淆

```cpp
ESP_GATTC_OPEN_EVT          = 2
ESP_GATTC_WRITE_CHAR_EVT    = 4
ESP_GATTC_CLOSE_EVT         = 5
ESP_GATTC_SEARCH_CMPL_EVT   = 6      ← 服务发现完成
ESP_GATTC_SEARCH_RES_EVT    = 7
ESP_GATTC_NOTIFY_EVT        = 10     ← 数据到达（不是 6！）
ESP_GATTC_CFG_MTU_EVT       = 18
```

我曾误以为 event 10 是 `SEARCH_CMPL`，导致绕了弯路。**实际 10 就是 NOTIFY，数据一直在正常到达。**

### 8.5 macOS 本地网络权限

在 M1 上，**Python 和 Chrome 都无法直连局域网**，但 `curl` / `nc` 可以。

- 命令行 `python3` → `Errno 65 No route to host`
- `open -a Python.app` 启动 → ✅ 正常
- Chrome → `ERR_ADDRESS_UNREACHABLE`

原因是 macOS 的本地网络隐私权限绑定在 **App Bundle** 上，不是可执行文件路径。

**绕过方式**：把 Python 脚本写成文件，用 `open -a .../Python.app --args script.py` 启动，结果写文件再读。
